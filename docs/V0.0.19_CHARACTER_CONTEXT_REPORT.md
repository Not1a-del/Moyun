## 调查结论

### 备份里的资料与当前发送并不是一回事

只读检查用户提供的约 200.7 MB 备份，随后在临时 Edge 资料中经现有原生导入流程导入。私人书稿不入库、不外发，原文件 SHA-256 前后相同。

| 检查项 | 结果与含义 |
| --- | --- |
| 正文与内置记忆 | 311 章；516 条已存记忆，其中 311 条与现存章节有效对应；57 组合并记忆。205 条历史记录仍保留，没有强行关联。 |
| 独立角色档案与关系 | `characters` 是空数组，因此独立角色关系也是 0 条。不能说是本轮发送函数丢掉了这份备份里的角色数组。也不能仅凭此文件证明角色从未建立或更早没有丢失，需与更早仍正常的备份对比。 |
| 世界资料 | 世界观 9,576 字符，另有 6 条资料，其中 3 条势力；势力成员关联为 0。人物信息可能散在自由文本、正文及记忆里，不能据角色数组为空说“全书没有人物设定”。 |
| 当前默认请求 | Gemini 输入改写／抗截断全关与全开各发 1 次本地 mock 正文请求，同章复测均为 69,412 字符，57/57 组记忆进入。第三人称规则存在。世界观首部进入、尾部没有完整进入，6 条资料的完整摘要与详情都未命中该次最终请求。 |

| 备份内历史请求 | 最近三份生成快照对应第 297／304／309 章，消息合并长 518,369／533,963／541,740 字符。最大历史请求 552,237 字符。它们不是当前版本重建的请求，也不证明服务商实际收下了全部输入。 |

当前请求比历史快照小得多，不能用历史 54 万字符来描述当前请求。上轮“57 组已进入请求”的结论仍成立，但它只证明记忆覆盖，不证明人物资料完整、事实正确、没有矛盾或模型遵守。

世界观中 2 处“性格”字样全部位于第 4,000 字符之后，4 处“关系”字样中有 3 处在该位置之后，说明裁剪区域确实涉及人物相关描述；关键词本身不能代替事实核对。字符数不等于 Token 数，备份内的历史消息也不能用来推算用户当前服务商实际接收窗口。

最终请求进一步逐项匹配关键词附近的原文片段：2 处“性格”中有 1 处、4 处“关系”中有 1 处未命中。其他片段可能从记忆等部分再次带入，不能将“位于世界观裁剪范围外”直接等同于“该事实一定没发”。本次只输出这些计数，没有保存相关私稿片段。

### 合成角色实际请求复现了资料漏项

用 3 个角色、双向关系、性格标签、说话方式、专属约束和本章细纲运行现有 `startGeneration`，捕获最终 HTTP 请求体；不是只检查中间预览。

- 默认自动选材命中本章角色后采用摘要模式：简介在，关系、说话方式与专属约束不在。原因在 `buildStoryBibleContextPreview` 的摘要／详情字段差异，非流式解析丢字。
- 将同一角色显式设为详情模式后，同一章的说话方式、约束和关系均进入请求。两组场景均覆盖 Gemini 双开关全关／全开，使用同一章号，避免上一轮假正文改变下一轮选材。
- 传统角色串按头部裁剪，后排角色仍有被裁掉的风险；自动命中角色之后，其他角色不一定进入。应区分作者主动排除、未命中与预算排除。
- 关系图读取原角色关系，AI 读的是关系文字，并不读 SVG 颜色。本书备份没有独立关系记录，所以图谱颜色 bug 不能直接解释它的全部人物混乱。
- 第三人称规则存在只能排除“整条人称要求完全没发”；目前缺少明确的本章视角人物、称谓与称呼对象约束，无法由第三人称一句话保证代词和亲属／师徒关系正确。

## 建议方案与可行性（本轮未实施）

建议先做第 1 项，以较少代码修复已证实的漏项；其后再评估是否需要收紧记忆选材。不要直接删除旧记忆，也不要把百万字原文无差别全塞进请求。

1. **本章人物关键事实完整保留。** 在现有资料包里分清可压缩简介与必须保留的姓名／性格底线／专属约束／关系方向／阵营／当前状态。摘要模式也带关键事实，优先保留本章参与者；预算不足明确列出未送项，不能静默截断。沿用现有 always、钉选、排除与详情设置，兜底不得反向带回作者明确排除的角色。可行性高，不必改书库或加一套角色存储。
2. **按本章问题找旧事实，记录来源和时点。** 最近正文、已确认长期事实、本卷交接与本章相关旧记忆分层组织；同一事实的旧状态标明章节范围。先按人物名／别名、关联 ID、章节和关键词召回，向量作为补充，失败有文字回退。保留完整旧库，可查看每次选中了什么、没选什么。可行，但有“漏召回”风险，不能仅以变短作为成功标准。
3. **把方向与称谓写清楚，处理冲突。** 用“记录者 A → 对象 B，关系原文……”表达，不能自动倒置师徒、父子或猜出称呼对象；可由作者确认本章视角与称谓。作者确认的设定优先，历史记忆保留发生时点；资料冲突提示作者，而不是让模型凭偏好解决。结构化校验可行，任意自然语言关系的判断不能保证完全正确。
4. **对空角色库提供可审阅的整理办法。** 从已有世界观和用户选定的正文／记忆提取候选档案，列出出处，作者接受后才写入。不能按 0 条角色记录自动编造人物，不能覆盖旧自由文本。可以做，涉及 AI 调用和候选审阅，需作为下一轮独立改动。

方案验收必须同时检查：最终请求含关键事实、错误分支内容不进入、预算缩小时无静默漏项、主动排除仍有效，以及同一真实失败章节用原服务商复测后的人设／关系／代词是否改善。需要作者提供更早仍正常的备份或当前真实失败请求，才能区分早期资料缺失和本轮发送选材。

## 本轮已修复

- 角色工作台基本档案新增“阵营 / 势力”：可勾选已有势力、进入原资料编辑器、新建势力。与世界资料 `characterIds` 共用一份稳定 ID 关联，不新增阵营副本或 localStorage 键。
- 未关联角色的势力也可显示；图谱与筛选按资料的 `name` 显示，保留旧 `title` 回退，修复实际有名称却显示“未命名势力”。
- 关系状态识别优先分清合作、敌对、警惕等，修正“盟友”被单字“友”识别为亲密、“并不信任”显示信任色；当前态空时参考关系类型。
- 合并线按状态分类比较。“信任”和“亲近”保持同类状态色；不同状态用带说明的虚线，详情分别展示 A → B、B → A 的原事实和颜色。不会为统一颜色改写关系。
- 角色关系新增固定“图谱状态色”选择，默认自动识别；复杂、未识别描述可手选分类，不依赖随意颜色值。分类存进原关系记录的 `statusKey`，随原书保存／导出／导入。它只影响图谱，不能当作 AI 已读到关系文字。
- 节点颜色明确标注为区分人物，避免与关系状态色混淆。
- 原连线代码没有读取用户任意 `color` 的路径；已复现的是文字误分类、同类状态被判混合以及阵营名称字段读错，不能笼统归因为“全用了自定义色”。
- 平板／窄桌面不再同时挤入角色索引、编辑器与检查器：复用原下拉选择和折叠检查器。1024 宽编辑区从 114 增至 564 px，768 宽从 78 增至 308 px；保持主应用的平板双栏。

## 更新说明、边界与回滚

用户可在角色档案调整阵营成员，在关系编辑里选择固定状态色；图谱保留双方关系方向。手机与平板角色编辑区使用现有简化布局。没有新增 AI 请求，不改公告、不提升版本、不改预设 golden 文件，不碰原私人备份。

最没有把握的是原用户模型对既有长篇事实的遵循：本地 mock 只能证明发送内容，不能证明真实续写的正确性。最重要的遗漏是“写在资料里”不等于“本轮发出了关键事实”，而“发出”也不等于“事实没有过时”；这两层均需下一轮方案处理。不能宣称全部记忆／人物混乱已解决。

尚未做真实服务商续写、用户真机和线上发布验收。还没有更早的正常角色备份供逐项对比。自动状态词识别仅是展示辅助，不是完整的自然语言关系推断。

回滚可回到基线 `3a052bd`，或撤销本修复分支上的本轮提交后重新构建。不删书库、不迁移角色资料；`statusKey` 是原关系上的可选展示字段，旧版本可忽略，原关系原文未被覆盖。后续如需上线仍先公测，再经用户确认候选后正式发布。
