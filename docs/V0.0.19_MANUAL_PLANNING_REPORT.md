## 更新内容与操作

自动解析沿用上一轮的服务商无关解析器，不为某个模型另外写一套规则。本轮补充人工处理路径：应用不能安全采用的规划，用户可以阅读保留下来的文字，明确选择去向，再确认写入。手动整理本身不调用 AI。

入口包括大纲／卷纲失败审阅中的“手动选择并填充”、一键开书“设定与大纲”失败模块的原文区，以及单章细纲格式异常询问中的“手动采用”。大纲工作台可通过“继续手动整理原文”恢复草稿；一键开书原文在刷新后仍可从工作台的未完成原文区进入。

1. 打开“手动整理 AI 原文”，在只读原文框中选择文字，点“填入选中文字”；也可复制粘贴，并修改待填内容。重复填入会追加到编辑框。
2. 选择故事大纲、卷纲、章节细纲、书名、作品简介、世界观或负面要求。默认追加保留原内容，明确选择后才替换；书名为替换。卷纲需指定已有卷或填写新卷名、起止章；细纲需指定章号。
3. 点“加入待确认列表”，可以继续分配其他段落。一个目标只保留一项，避免多项互相覆盖；需要调整时先移除该项再分配。尚未加入列表的编辑文字不会被悄悄忽略。
4. 点“查看写入对比”。电脑左右显示原内容和确认后的内容，手机上下显示，内容区独立滚动。点“确认写入 N 项”才改正式数据；也可返回调整或保存草稿返回原失败页。

仅新增或修改明确选中的分区。新卷范围与已有卷重叠时整批阻止；手动新增细纲按章序补入，不猜测生成跳过章节。全书大纲、卷纲与书籍设定沿用原有共享规则，细纲只写当前分支，界面已说明。手动填入部分内容不会自动把整个一键开书失败模块标为完成，避免误报。

## 保存、冲突与回滚保护

- 完整规划文字、编辑框、待确认列表和上次写入状态存放在 `novel.reviewStates.manualPlanning[branchId]`，通过原来的 `DB.saveLibrary` 保存；没有新增 localStorage 键或 IndexedDB 库。
- 关闭和普通输入沿用防抖保存；确认写入走现有 `saveDataNow` 的排队与重试流程。刷新后可以继续整理。
- 查看对比后，确认时再次检查书籍、分支和原内容基线。原内容已变化则不覆盖，要求重新查看对比。正在生成时不能确认写入。切书或切分支自动关闭弹窗，草稿仍归原书、原分支。
- 新原文遇到未完成草稿时先询问继续旧草稿还是改用新原文。上次已写入但保存失败时，不能直接丢弃待保存状态。
- 保存失败时保留页面内容及原文，显示“重试保存”；重试只保存，不重复执行追加。只有保存流程返回成功才提示手动填入成功。
- 旧细纲沿用 `archiveChapterOutline` 历史规则，卷纲保留原有交接及关联元数据；内容没有变化的目标不会增加历史或标记过期。历史数量／长度仍遵循原项目限制，不能把它当全量备份。
- 按分支导出、导入时，同时筛选并重映射手动草稿；导入成新书后重新绑定当前书籍。删除支线只清理这一支的草稿。
- 未确认的手动草稿留在原分支，不随新分叉复制，避免把分叉点之后的待填目标误带入子分支；已经确认的细纲依旧由原有分支复制规则处理。

## 测试环境与实际输入

命令均在主目录执行。浏览器使用本机已有 Edge、临时独立资料目录和本地 HTTP 页面，不连接用户日常浏览器，也不调用真实模型。

第一组模拟响应故意不提供可自动分卷的结构：

> 这是模型自定义的策划格式，自动解析失败，但文字仍可阅读。
> 故事走向 → 主角收到港口来信，开始调查旧档案。
> 后半卷安排 → 调查员核实邮戳，再沿海岸寻找寄信人。
> 第一章细节 → 主角检查信封，发现已经褪色的火漆。

通过页面实际 `generateOutline` 入口发出 OpenAI-compatible SSE 模拟请求，连接为 `https://manual.invalid/v1`、模型 `local-mock`。将三段文字分别追加到大纲、替换第一章细纲、新建第 3–4 章的卷纲。确认前正式数据保持哨兵值；确认后新内容正确、旧细纲历史与原卷交接保留。下一次规划请求体包含最新大纲、细纲、新卷及原交接。

第二组从实际单章细纲生成入口返回“第99章”开头的 37,425 字回复，目标本应是第一章：程序不自动覆盖，出现“本章细纲格式异常”询问。点击“手动采用”，选取原文末尾段落，明确放入第一章细纲，确认后写入；刷新后完整原文、采用内容、旧细纲历史仍在。该流程总共只有原生成的一次模拟请求，手动操作不增加请求。

布局覆盖 `1280×800`、`360×740`、`320×740`，各测浅色和深色，共六组。通过 CDP 鼠标点击实际按钮；文本选区使用 textarea 原生选区属性与 select 事件，未冒充手机真机长按。检查弹窗视口范围、正文独立滚动、无横向溢出、底栏按钮至少 44px 的最终样式及点击中心没有遮挡。已查看电脑与手机、深浅主题的原文和对比截图。

手动路径没有新增 AI 请求。独立手动测试中的深浅主题分别同时开／关 Gemini 输入改写与抗截断，但使用的是 compatible 的 local-mock；不能据此声称已验证 Gemini 协议。原生 Gemini／compatible 两种协议、全开／全关的规划请求与中断矩阵由下列既有规划恢复浏览器检查另行覆盖。

## 未覆盖与需要继续关注的地方

- 本轮不请求真实 Gemini、DeepSeek 或其他服务商，不把本地模拟写成真实兼容性通过。未来无法识别的可读规划可以由用户手动分配，但不能保证所有模型输出都可自动解析。
- 最没有把握的是 iOS／Android 真机长按选区、软键盘与系统复制菜单的组合；桌面 Edge 的移动尺寸和原生 selection 事件不能代替这些环境。保留了复制粘贴路径，需要用真机复验。
- 人工分配只验证字段、章号、卷范围和确认时的内容冲突，不判断剧情是否合理。用户仍应阅读对比，尤其是跨卷衔接和替换已有细纲。
- 本轮的新分区界面覆盖大纲、卷纲、单章细纲和一键开书核心规划失败；没有扩展成角色、文风或全部团队专员的通用 JSON 编辑器，这些入口仍按原有专用编辑／重试流程。
- 未做百万字原文、浏览器强杀／断电、真实配额耗尽的端到端测试；37,425 字完整原文与真实刷新已测，保存失败使用独立逻辑模拟验证。
- 最大的后续风险是用户把“已手动填入部分内容”误认为整个失败任务已完成。因此保留失败模块和原文，不自动宣布整模块成功。
