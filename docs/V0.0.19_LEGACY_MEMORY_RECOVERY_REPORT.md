## 根因与最小改动

| 位置 | 原行为及影响 | 修复 |
| --- | --- | --- |
| `buildBudgetedChapterHistory` | 合并记录实际只有 `key`，去重却使用 `group.id`，各组都变为 `g:undefined`；长书只发第一组。缺 `id` 的范围总结也会同样漏发 | 按本次选中的记录对象去重；不改存档结构，无需重建记忆 |
| `buildChapterHistoryContext` | 新卷第一章用上卷交接替代正文时，把更早卷的上下文也排空 | 上卷仍由交接替代，更早卷用摘要和长期记忆补齐，不额外带旧卷正文 |
| `adoptLegacyLibrary`、`loadData`、`initBooks` | 旧库字段白名单遗漏书内记忆／MOD等资料；部分顶层旧资料首次切书后消失 | 复用 `restoreLegacyBookContext`，只给旧当前书补缺失字段，不覆盖书内已有值或主动清空数据；首次建书架即同步书内资料 |
| `resolveImportedBookData` | 旧书架 JSON 中仅在顶层的当前书记忆没有导入 | 沿用同一个补缺函数，不修改备份对象，不拷全局 API 密钥 |
| `mergeBookTransfer` | 只有顶层规划的旧备份导成新书后，被新书默认的空主线规划遮住 | 仅在备份没有 `branchData` 时把原有顶层规划补入主线；明确存在的分支数据不被覆盖 |
| `regenerateMemory` | 先删除旧记忆再请求，失败或中止后无旧记录可用 | 复用补录流程强制重记指定章，成功后才替换旧记录 |
| `readBookTransferFile` | 超过 50MB 就拒绝 JSON | 删除该硬限制，其余校验与保存流程不变 |

已对照 v0.0.18 源码：记忆记录结构与正文指纹算法一致，没有证据把本例归因于指纹算法升级。没有关闭有效性或分支校验来强行启用过期记忆。

### 测试脚本中发现的问题

门禁首轮不计入通过。预设测试运行环境缺少新补缺函数、卷交接测试替身未返回 `missingChapters`，已补足依赖和返回结构。另把只匹配源码拼接字串的摘要测试改为真实调用断言：25,000多字交接、实际卷纲和目标章号完整。

浏览器回归首轮还发现：固定等待240ms仍可能在开关动画结束前测到3.019px；旧预设传输脚本跳转源码时仍写死4176端口。已分别改成等待实际动画结束、从隔离runner传入地址生成源码地址。几何与内容断言没有放宽，原始失败记录留存。

## 未覆盖与后续处理

- 未调用真实模型，因此只确认“正确的已有资料进入了请求”，不宣称模型已经完整理解并续写正确。下一步应由用户在修复候选上复查同一本书的真实上下文，再用原有模型生成一章核对事实。
- 205 条没有现存章节对应的记忆均标为主线，有205个独立正文指纹，与当前311章的记忆指纹没有重合。需核对曾删章或重写历史；本轮完整保留，不自行关联或清理，不能仅靠改chapterId把它们当作当前章事实。
- `regenSnapshot` 占备份约92%，本轮不删除或改写它。200MB JSON 在桌面隔离 Edge 已实测成功，不能据此保证低内存手机可导入任意大小备份；流式／分块导入和快照体积治理属于后续问题。
- 当前备份不能恢复其中本来就没有的历史正文，也不能证明其他用户旧档没有遭遇不同损失。缺少其他备份时不能声称恢复所有历史版本。
- 浏览器真实服务商差异、真机／iOS／厂商浏览器未验证。
