## 3 逐步存档与检查办法

### 3.1 分支与标签

- 起点是当前提交 114c9be（v0.0.18）。建集成分支 release/v0.0.19，打本地标签 v0.0.19-base。
- 层分支都从集成分支切出：v0.0.19/L1-foundation、v0.0.19/L2-data、v0.0.19/L3-generation、v0.0.19/L4-ui。

### 3.2 每一步的固定流程（逐步存档）

1. 开工前：git status 必须干净，确认在正确的层分支。先把本步要过的验收编号抄进 docs/V0.0.19_STEP_LOG.md 的新条目，先写清单再写代码。

3. 自检：npm run build，再 node --check assets/js/moyun.js，再 npm run audit，再 npm run regress，再跑本步相关专项脚本，最后做浏览器多宽度实测（见 3.4）。
4. 记录：填步骤记录。没过的验收如实写「未过」，不得改成「基本通过」。
5. 存档：git add 指定文件（npm run build 重新生成的 index.html 和 assets/ 是否入库以仓库现状为准，S0 确认）。git commit，再 git tag v0.0.19-sN。
6. 回看：git show --stat 确认这个提交只含本步相关文件。
7. 一步没做完需要中途保存时，提交信息写 wip(v0.0.19-sN)，不打标签。步骤做完才有带标签的提交。

### 3.3 回滚办法

- 单步不过：git switch -c v0.0.19/fix-sN v0.0.19-s(N-1)，在新分支重做，原分支保留不删。
- 单层不过：不合入集成分支。
- 整版放弃：回到 v0.0.19-base。
- 回滚后必须重新跑 build 和 audit，确认旧状态能正常启动。步骤记录里写明回滚位置。

## 4 地基部件

### G1 AI 回复兜底

原则：能用多少收多少，只丢坏的那一部分；全坏也不丢，原文留给用户。

格式：短结构（拆分方案、卷纲、清单）用 JSON；长文字（细纲、扩写、大纲）用标记块，例如【新内容开始】…【新内容结束】。长文字塞进 JSON 容易因引号换行出错。

统一写 parseAiStructured(原文, 格式说明)，按五级处理：
1. 提取：去代码围栏和客套话，找第一个完整的 {} 或 []，容忍尾逗号、中文引号、单引号。
2. 补默认：可选字段缺了用默认值，类型能转就转（「第3章」转 3，「a、b、c」转数组）。必填字段缺失才算这一项无效。
3. 只丢坏项：10 项里 8 项有效就收 8 项，其余标「需补」。
4. 修复请求：把原文发回 AI，只让它按格式重排不改内容，只试 1 次。被截断的复用 v0.0.18 的抗截断续写。
5. 最后兜底：原文留在草稿区，显示「格式异常」，三个按钮：重试、复制原文、手动采用。长文类可直接把原文当正文采用。

各场景兜底：

| 场景 | 缺失或错误时 |
|---|---|
| 拆分方案 | 缺项用默认。角色名缺失由角色员自起，汇总登记。整体坏了走第 4、5 级，最后给手动填写方案的表单 |
| 卷纲规划 | 好的卷留下，坏的卷丢。范围校验不过让 AI 修一次，仍不过按总章数均分 |
| 细纲批次 | 复用现有分章解析。缺章只重试缺的章，多出的章丢弃并提示 |
| 设定修改清单 | 缺理由可空。缺原文片段时，短条目可整条替换，但必须用户勾选确认 |
| 扩写返回 | 没有标记就剥掉「好的，以下是…」取正文。仍异常就照样给预览，加警告，由用户决定 |
| 衔接检查 | 坏了显示「检查结果无法解读」并附原文，不当成「没问题」 |
| 反推大纲单段摘要 | 只重试坏的那一段，仍坏用该段细纲前 100 字代替 |
| 审查 | 坏了跳过自动修复，原文给用户看，标「审查未完成」 |

安全线：自动重试最多 2 次（带上次错因）；另加最多 1 次修复请求；用户点停止后不再发任何请求；AI 明确拒答不按格式错误处理，提示「模型拒绝了，可改写要求或换模型」；原始回复只放内存，最多保留最近 20 条，不进存档。

验收：
- F-01 合规 JSON 一次通过，没有额外请求
- F-02 带代码围栏和客套话，正确提取
- F-03 尾逗号、中文引号、单引号，容错通过
- F-04 缺可选字段，用默认值不报错
- F-05 10 项中 1 项缺必填，其余 9 项入库，坏项标「需补」
- F-06 类型错误自动转换
- F-07 JSON 被截断：先救出完整的项，再续写或修复 1 次
- F-08 全是废话没有结构：修复 1 次，仍不行保留原文并给三个按钮
- F-09 AI 拒答：提示「模型拒绝」，不当格式错误
- F-10 返回 HTML 错误页或空串：白话提示加重试
- F-11 标记块缺结束符：取到文末并提醒
- F-12 标记块重复或嵌套：取第一个完整块，其余忽略并提示
- F-13 重试次数不超过上限（2 次重试加 1 次修复）
- F-14 重试提示词里带有上次错因
- F-15 复制原文复制的是未经处理的原始回复
- F-16 原始回复不进存档（导出文件里搜不到）
- F-17 用户点停止后不再发任何请求
- F-18 多块并行时，一块解析失败不影响其他块

### G2 通用红绿审阅部件

现状：对比引擎 createDiffRevisions、applyRevisions 和样式 .diff-del、.diff-ins 本身是通用的。写死给大纲的是状态（outlineRevisions、selectedRevId、outlineRevisionUndo）和大纲工作台里的一段界面，状态还会随书保存和恢复（多处读写）。

要求：
1. 抽成「工厂函数加组件」，每处使用有自己独立的状态，组件注册方式照现有写法。
2. 原有功能原样保留：逐块接受或拒绝、全部接受、全部拒绝、含删除时先提示删除段数和字数、应用后一键撤销、待审状态随书保存（刷新后还能继续审）。
3. 新增：每块可勾选，默认全勾，「无法定位」和「超出范围」的块默认不勾且不可勾；每块有来源说明（例如「理由：统一势力名称」）。
4. 先让大纲审阅改用新部件，确认行为与改前一致，再给项目3、5、6、7用。旧代码清掉，不留两套。
5. 界面：顶部「全部接受、全部拒绝、应用所选(3/5)」；每块一张卡片，标题行写块序号、位置、理由；红色旧文、绿色新文；按钮「应用」「只看这块」。手机上单列卡片，按钮不小于 44px。

验收：
- W-01 大纲审阅逐项对照改前：接受、拒绝、全部接受、全部拒绝
- W-02 含删除时的二次提示显示删除段数和字数
- W-03 应用后一键撤销，大纲回到改动前，修订重新进入逐项审阅
- W-04 审阅到一半刷新或关闭重开，待审状态还在
- W-05 切书后再回来，待审状态属于原书，不串书
- W-06 两个审阅同时存在（例如大纲加设定修改）互不干扰

### G3 衔接守卫

问题本质：改了一章，相邻内容还停留在旧版本，AI 再写时就会前后矛盾。守卫只做三件事，不做第四件：

1. 提醒：book.staleMarks 记录「哪一项因为谁变了，需要核对」，字段 {id, kind, targetId, branchId, reason, srcId, at}，kind 分细纲、卷、正文、卷末交接。被标记的卡片显示黄色小标签「待核对」，点开看原因，点「已核对」消除。全书最多 200 条，超出删最旧；删除条目时同步清理；按分支分开记，不复制到新分支。
2. 检查：通用函数 checkContinuity(类型, 左项, 右项)，返回问题清单（位置、类型：冲突或断层或重复、说明、建议）。没问题时 AI 必须明确输出【无问题】。冲突默认显示，建议默认折叠，避免过度挑刺。
3. 提议：用户点「让 AI 调整相邻章」后，AI 给出调整稿，一律走 G2 红绿对比，用户逐章确认。任何情况下都不自动改相邻内容。默认只调整前后各 1 章，且限同一卷内。调整后只给下一个相邻章打标记，不连锁调用 AI。

各场景：

| 重新生成的对象 | 生成前 | 生成后 |
|---|---|---|
| 单章细纲 | 提示词带前一章和后一章的完整细纲（各限约 600 字），加硬约束：不得改变相邻章已确定的事实；本章结尾要能接上后一章开头；确需冲突时在末尾单独写一行【衔接提示】说明 | 解析【衔接提示】，同一次请求里完成初检，不额外耗请求；相邻两章打「待核对」 |
| 多章细纲 | 范围外紧挨着的前一章和后一章设为「锁定」，只读不改，两端都给 AI | 检查范围两端的衔接，加范围内相邻章之间的衔接，合并成一次请求 |
| 卷纲 | 带相邻两卷的衔接点和上一卷实际交接 | 相邻卷和卷内细纲打「待核对」 |
| 大纲 | 沿用现有红绿审阅 | 审阅完成后比较卷范围和卷摘要是否变化，报告「影响 X 卷 / Y 章细纲」，全部打「待核对」，由用户决定要不要重排细纲 |
| 正文 | 沿用现有 | 下一章的正文和细纲打「待核对」；本章在已生成卷末交接的卷内时标「卷末交接已过期」；章节「更多」新增「衔接检查」：本章末尾约 600 字对比下一章开头约 600 字 |

两个开关（设置里）：「重新生成后自动检查衔接」默认开；「允许 AI 微调相邻章」默认关。

验收：
- C-01 单章细纲重新生成时，提示词里带有前后章完整细纲（真实上下文或抓包核对）
- C-02 多章重写时，范围外紧邻的前后章被锁定，生成后这两章一字不变
- C-03 造冲突：第 5 章改成「主角死亡」后重新生成第 4 章，能提示第 4 到 5 章的问题，且不自动改第 5 章
- C-04 「让 AI 调整」一定出红绿对比，确认后才写入
- C-05 检查结果格式坏了，显示「无法解读」并附原文，不显示「没问题」
- C-06 关闭自动检查后，生成流程与现在一致，没有额外请求
- C-07 待核对标签可点开看原因，「已核对」后消失
- C-08 删除章节后相关标记同步清理
- C-09 标记超过 200 条时最旧的被删，不报错
- C-10 新分支不继承待核对标记
- C-11 大纲、卷纲、正文各一个场景实测，相邻内容都被正确标记
- C-12 刷新后待核对标记仍在
- C-13 AI 微调只能动同卷内前后各 1 章，不连锁
- C-14 手机上提示条和标签不撑破卡片

### G5 存储与性能

存储位置：
- 书的数据继续走 DB.saveLibrary 存进 IndexedDB（NovelWriterV6）。新数据只挂在书的数据里一起存。
- 紧急备份（localStorage，轻量）保持轻量：写主线版本的细纲和暗线，并记录当时所在分支，不写 branchData。恢复时记录的分支不是主线，不得把分支内容写进主线字段。
- DB.saveLibrary 在 IndexedDB 失败时会退回 localStorage（容量小），这种情况必须提醒用户。

接近上限提醒：写 checkStorageQuota(原因)，用浏览器自带的 navigator.storage.estimate() 取已用和总量。浏览器不支持时，只在保存失败时提醒。

| 占比 | 提醒 |
|---|---|
| 80% 以上 | warning：浏览器分给本站的存储空间已用约 X%，建议尽快导出备份 |
| 90% 以上 | error，停留更久：存储空间快满了，请现在导出备份 |
| 97% 以上 | 一键开书、批量生成、新建分支前，先用 openConfirm 提示风险 |

检查时机：页面启动、切书、保存后（最多每 5 分钟一次）、创建分支后、一键开书结束后。同一级别同一次打开页面只提醒一次，升级再提醒。用户导出过备份后，本次打开页面内不再提醒 80% 级，90% 级仍提醒。

失败处理：保存失败（含 QuotaExceededError）弹持久 error toast「保存失败：浏览器存储空间不足，请立即导出备份」，内存数据保留，不假装保存成功。保存实际落到 localStorage 备用位置时弹 warning「浏览器存储异常，数据暂存在小容量位置，请尽快导出备份」。toast 要带导出备份入口；showToast 不支持按钮就在文字里写清入口位置（S0 先找到现有导出入口）。

性能底线：
1. 分支只存分叉之后和改过的部分，不整份复制。
2. 分支面板、阅读视图、路线图、占用统计点击后才创建，关闭即销毁。
3. 切换分支只处理当前和目标两份数据，不遍历全书。
4. 长列表用 content-visibility:auto 并写 contain-intrinsic-size，避免滚动跳动。
5. 细纲历史每章最多 3 条、每条上限约 3000 字；待核对标记全书最多 200 条；历史和标记都不复制到新分支。
6. 分支超过 8 条时提醒占用。每条分支的约占用（KB）只在面板打开时计算。
7. 现有保存是整个书库写一次。S0 用「100 章加 3 分支加 30 条设定」的书实测保存耗时，超过 500 毫秒先把数据交给用户再决定怎么优化，不擅自改存储结构。

验收：
- K-01 伪装 navigator.storage.estimate 为 80%、90%、97%，三级提醒分别出现，文案正确
- K-02 同一级别不重复弹，升级后再弹
- K-03 导出备份后 80% 级不再弹，90% 级仍弹
- K-04 模拟写入报 QuotaExceededError：出现持久 error toast，内存数据不丢，可继续导出
- K-05 模拟 IndexedDB 不可用：出现「数据暂存在小容量位置」提醒
- K-06 本版新增数据（分支、历史、标记、卷字段）在导出文件里都能找到，导入后完整恢复
- K-07 新增代码没有写入新的 localStorage 键存书数据
- K-08 API 密钥、主题的存取行为与改前一致
- K-09 紧急备份记录了分支，在分支上恢复不污染主线
- K-10 保存耗时实测数据写进报告（夹具 C）
- K-11 一键开书和批量生成前，97% 时有确认提示
- K-12 不支持存储估算的环境（例如双击打开本地文件）不报错，只在保存失败时提醒

## 6 各项目

### 项目1 分支（正文、大纲、细纲、暗线）

**a 项目问题**
- 细纲和暗线全书只有一份，分支写作读到的是主线内容，会串线。
- 范围总结新建时不记分支，读取只按章号匹配，有串线风险。
- 暗线只认主线章号，分支里「本章布置、推进、回收」全部停用。
- 没有直观的分支图，只有文字版故事树，分支入口分散，各工作台里看不到当前在哪条分支。

**b 要求**

1. S4 体检（先于一切分支新功能）：建书写 3 章，从第 2 章分叉再写 2 章，用写作框旁的「真实上下文」逐项核对支线生成时收到的前文、记忆、总结、细纲、暗线、章节索引，每项给「安全或串线」的实测结论。只修后续读取，不修历史数据：新建范围总结时记分支编号（旧总结按主线）；读取时主线只读主线的，支线读「分叉点及之前的主线总结加自己的」；改动位置是总结写入处和 buildChapterHistoryContext。
2. 支线里不能再分叉：forkBranch 拦住并给白话提示；章节「更多」里的「分支重写」在支线里置灰并说明原因（分支里不能再分叉，请先回到主线）。这一限制写进更新公告。
3. 数据结构（只存分叉之后的部分）：

```
book.branchData[分支id] = {
  outlineTail: [...],            // 分叉章之后，本分支自己的细纲
  outlineEdits: { 章节id: 内容 }, // 在本分支里改过的分叉章之前的细纲
  darkline: [...],               // 暗线整份
  note: ''                       // 本分支走向，最多 200 字
}
```

4. 分叉位置沿用现有 branchList 里的 forkIndex，不重复存。主线继续存在原字段 chapterOutlines、foreshadowMatrix，不迁移，所以老版本打开新存档只是看不到分支细纲，不会坏。页面里的 chapterOutlines、foreshadowMatrix 永远是「当前分支看到的那份」，所有现有读取细纲的代码一行不改。
5. 写 swapBranchScopedData(从, 到)：存回当前分支，取出目标分支。到分支时，页面细纲等于主线前 N 章（克隆）加本分支改过的加本分支自己的；存回时与主线对应章逐项比较，只保存有差异的。
6. 保存、导出、备份、恢复时统一经 getPersistedOutlines() 取「主线版本」写入原字段，分支部分写入 branchData。不管用户当时在哪条分支，原字段里永远是主线。需要同步的位置约 10 处（BOOK_FIELDS、保存、加载、切书、备份恢复、导入导出、一键开书写入、紧急备份等），全局搜 chapterOutlines、foreshadowMatrix、snap( 逐处核对，一处不漏。
7. 加载时存档里 activeBranchId 不是主线，加载后立刻切到该分支。
8. 新建分支：前 N 章细纲视同主线，之后空白（后续全新）。暗线复制整份，并清掉分叉章之后的「实际回收」。历史和待核对标记不复制。
9. 老书（有分支但没有 branchData）惰性迁移：用户第一次进入或编辑该分支时，才为它建 branchData，把主线分叉章之后的细纲复制成它自己的 outlineTail，行为与以前一致。没进过的分支不占空间。
10. 删除分支：同时删 branchData 里的数据；确认框用 impactLines 写明将删几章正文、几章细纲、约占用 KB。
11. 大纲（总纲）和卷纲仍全书共用一份，不分支。每条分支只多一个可选的「本分支走向」备注，写作和写细纲时注入提示词。

### 项目5 开书

#### 5-A 一段话团队开书

**a 项目问题**：现在开书要填很多项，AI 一步接一步顺序生成，一次写到结局，用户没有机会先看思路。

**b 要求**
1. 入口：新建书籍弹窗（openNewBookModal）左下角放「一段话开书」按钮（btn-ghost），右下保留原有取消和创建。点击后弹窗内容换成只有一个大输入框，用户想到什么写什么；右下「发送」，左下「返回手填」。原有手填入口不改动。
2. 团队流程（改造 startOneKeyGeneration）：

```
策划员  一次请求：拆分用户的话，输出方案和任务分配
  展示方案，用户确认
专员    并行：设定员、角色员、大纲卷纲员
细纲员  按卷并行（卷内批次仍按顺序）
汇总    程序合并、统一名称；必要时一次小请求定简介
审查员  一次请求，只看摘要
输出    写入书；已有内容的走红绿对比
```

模型分配沿用一键生成现有的模块与模型分配（S0 对照 getOneKeyRequiredModelKeys 确定），不新增模型设置项。
3. 策划员的输出（短 JSON，走 G1）：用户原话里明确说了的事实清单（标来源：用户或 AI 补充）；书名候选、类型、基调；「设定总表」（书名、角色名单含一句话、各卷卷名和章节范围）；它不确定想问用户的地方；各专员的任务目标和依赖。
4. 确认环节：方案以卡片展示，三个按钮「接受并开写 / 改一句再拆 / 取消」。点接受之前，书里不会有任何新内容。卡片写明「预计约 N 次请求」。设置里可勾「以后不再确认方案」，默认不勾。
5. 专员并行：所有专员都收到「设定总表」，书名、角色名、卷名都以它为准。沿用现有流式请求、失败自动重试、中断（okStreamFetch）。并发数由用户的 API 自己决定，不另做限制；遇到 429 这类限流按失败处理，单独重试。每块有独立状态：排队、进行中、完成、失败；失败的块可单独重试，不影响其他块；结果先放草稿区。
6. 汇总：程序合并各块；扫描各块里和总表对不上的名字，能确定时替换回总表里的名字，不能确定的列出来；补齐编号。
7. 审查：一次请求，读摘要（总表加大纲加卷纲加各章细纲前 80 字），不读全文。查：用户原话是否都落实（逐条对用户事实清单）、名字和设定有没有前后冲突、章节有没有断层、未完模式下有没有偷偷写结局。能自动修的（名字、范围）程序直接修，不能的列给用户。用户可点「让对应专员重做这一块」。自动审查只跑一轮。
8. 输出：新书里全是空白，在一次保存里一起写入，不会写到一半。已有内容的书（例如「继续规划下一段」），已有位置一律先走 G2 红绿对比，空白处才直接写入。写入前自动 saveSnapshot（一段话开书前）。有块失败时，用户可选「先写入已完成的部分」，失败的块标「需补」。
9. 进度界面（沿用 moyun-do-card 行和 moyun-wb-stat 风格）：每行显示角色、状态（完成、进行中、排队、失败）、用时；失败的行有「重试 / 查看原文」；右上「停止」。手机上每行单列，状态用文字加图标，不只靠颜色。关闭弹窗时有任务在跑，先确认是否停止。

**c 验收**

- T-02 点「接受」之前，书里没有任何新内容（导出核对）
- T-03 「改一句再拆」后，方案按新要求更新
- T-04 确认卡显示预计请求数；勾「以后不再确认」后下次直接开写
- T-05 能看到多块同时生成；用同一段话与现有流程对比总耗时，数据写进报告
- T-06 所有专员的提示词里都带「设定总表」（抓包核对）
- T-07 人为让一块失败（含格式错误），只有这块重试，其他块不受影响

#### 5-B 未完模式

**a 项目问题**：AI 一次写到结局，用户想先写一段、以后再续，没有办法。

2. 记录 novel.unfinishedMode、novel.planReminded（已提醒过的位置，防重复）。
3. 「一段」默认 10 章（一卷），用户可自定义。
4. 效果：只写这一段的卷纲、大纲和细纲；大纲止于悬念，提示词明确禁止写结局，暗线不强制回收。
5. 「继续规划下一段」按钮（大纲工作台，仅未完模式下显示）：走「拆分方案、确认、并行生成」，输入框提示「接下来的思路和想法…」，只追加新卷、新大纲、新细纲，已有内容走红绿对比。

7. 「标记为已写到结局」文字按钮：关闭未完模式，只改状态不动内容；关闭后不能再手动勾回。

- U-02 已有大纲或细纲时，勾选项置灰并有原因说明

#### 5-C 细纲反推大纲

**a 项目问题**：有些用户习惯先写细纲再补大纲，现在没有这个能力。

**b 要求**
1. 大纲工作台新增按钮「由细纲反推大纲」（至少有 1 章非空细纲时可用）。先弹确认，说明「将读取 N 章细纲，约需 M 次请求」。
2. 分段处理：每 10 章一段，各段并行，每段让 AI 输出摘要、关键事件、出场角色、未收束的线索、是否出现结局迹象（短 JSON，走 G1）。然后一次请求合并出总纲文字加卷纲（用项目8的卷纲解析）。
3. 结局检测：AI 必须明确回答三个问题——是否已写到结局、依据是什么、有多大把握。程序再做关键词复核（最后 3 章是否含「结局、终章、尾声、完结」等）。两者不一致时，把依据摆给用户二选一，不自己做主。
4. 三种结果：已写到结局——生成完整大纲；没写到结局——自动开启未完模式，大纲停在细纲最后一章，不编造结局，提示卡写「细纲写到第 N 章，未发现结局，已按未完模式生成，方便您以后补充」，并提供「改为让 AI 补全结局」；无法判断——让用户选。
5. 这是「未完模式只能在没建大纲细纲时手动勾选」的合理例外：此处是系统在创建大纲时代为开启，并在提示卡里说明。
6. 大纲已有内容时结果走 G2 红绿对比，空白时直接写入。细纲有空章或章号不连续时跳过空章并在报告里说明。

### 项目7 沉浸模式（手写、扩写、文案）

**a 项目问题**：续写框提示还是「下一章剧情走向…」；沉浸模式下编辑是在窗口里滚动，字号不够大，手写体验不好；没有扩写功能，也没有读取选中文字或光标位置的能力，手机上选字手势难做稳。

**b 要求**

7A 文案：续写框和全屏输入框的提示都改成「接下来的思路和想法…」。改完全局搜 nextChapterPrompt 相关提示，确认没有遗漏。

7B 沉浸手写（基于现有 immersiveMode）：
1. 整屏滚动：沉浸模式下主内容区改成铺满整个屏幕的滚动容器（S0 先找到现在在滚动的元素），手指或滚轮放在屏幕任何位置都能滚，包括两侧留白；正文栏宽度不超过约 46em。
2. 字号放大：变量 --immersive-font，电脑 18px、手机 17px，行距 1.9；现有沉浸字号更大就沿用更大的；只作用于沉浸模式。
3. 自动增高：编辑框随内容增高，不出现内部滚动条；用 requestAnimationFrame 节流，上万字的章节不卡。
4. 悬浮工具条：屏幕底部居中，三个按钮「手写 / 扩写 / AI续写」，圆角风格沿用 .immersive-exit，不遮挡右下角退出按钮；向下滚动时自动隐藏，向上滚或点一下顶部时出现；手机键盘弹出时贴在键盘上方（沿用 visualViewport 处理和 --moyun-mobile-browser-bottom）。
5. 手写：点「手写」，当前章进入编辑（复用 startChapterEdit、tempContent、saveChapterEdit、isChapterEditDirty，不另造一套）。停笔 2 秒自动存草稿（草稿就是 tempContent，由现有保存流程带着存）；实时字数；显示保存状态；点「保存」才写入正式正文。
6. 随时从 AI 切到手写：AI 生成中，生成状态卡新增「我来写」。点击后停止生成（stopActiveGeneration），保留已生成的半截正文，直接进入沉浸手写。写新章时，半截内容成为新章草稿；续写已有章时，半截内容追加进该章的编辑草稿。S0 先查清停止后半截稿放在哪，现在会丢就改成保留。
7. 沉浸下的 AI 续写：点「AI续写」弹出底部迷你输入框「接下来的思路和想法…」，复用 nextChapterPrompt，发送即走现有续写流程。
8. 手机键盘：光标始终不被遮住。先实测现状，不足再补。Esc 优先退出标签模式，再退出沉浸模式。

7C 扩写（标签加红绿对比）：
1. 点「扩写」，正文变成只读的段落块（不弹键盘，不依赖系统选字）。段与段之间有「＋」点击区（手机不小于 44px）。标签只放在段与段之间。
2. 标签颜色、形状、文字都有区分（色盲也能分辨），颜色用主题变量：

| 标签 | 含义 | 颜色 | 形状 |
|---|---|---|---|
| ◆ 插 | 单个插入点 | --info | 菱形 |
| ▶ 起 | 区间开始 | --ok | 向右三角 |
| ◀ 止 | 区间结束 | --warn | 向左三角 |
| 整篇 | 通篇选择性扩写 | --accent | 圆角徽标 |

起和止之间的段落用淡色底。点标签可取消。顶部有图例条。
3. 标签数量决定模式：0 个标签——结尾扩写，接着当前结尾往下写；1 个「插」——在该处插入新段落；起加止——对中间的段落扩写或改写，可切换，没有额外要求也能用，不填默认扩写；点「整篇」——AI 通读全文，自己挑多处建议扩写。
4. 每种模式都有「想怎么扩（可不填）」和目标增加字数（默认约 500 字）。
5. AI 读全文，只改标签内：发给 AI 的是全文，每个段落带编号 P1 到 Pn，标签位置用编号标出，另附当前分支的本章细纲、上一章末尾、下一章细纲首句。要求 AI 只返回标签内的新文字，用标记块【新内容开始】…【新内容结束】。整篇模式返回清单，每条含「段落编号、插入或替换、新文字、理由」，用段落编号定位，编号无效再用定位句近似匹配。程序负责拼回；分段时记录原有分隔符，拼回后标签外的文字一个字都不变。格式兜底走 G1：没有标记就剥掉客套话；怀疑夹带了标签外的文字就裁掉并提示；长度明显偏离也照常给预览并加警告，由用户决定，不静默丢弃。
6. 结果用 G2 部件展示红绿，可逐块应用或取消。应用到的是编辑草稿，点「保存」才写入正式正文。生成时编辑区锁住，失败则正文不变。

### 项目8 卷纲多创建，细纲只读相关卷

**a 项目问题**
- AI 在写大纲时没有多创建卷纲的能力和想法：提示词里没教它，代码也只自动建第一卷（ensureDefaultNovelVolume），AI 只能修改已有的卷（约 9393 行的限制）。
- 细纲分批生成时只按每批第一章定卷，一批跨两卷就会读错卷。
- 卷里没有单独的「写作内容要求」字段。

**b 要求**
1. 先找根因（S0 实测）：抓一次真实的一键开书和 generateOutline 请求，核对提示词、解析（normalizeNovelVolumes）、创建函数，结论写进报告。
2. 给 AI「多卷」的能力和想法：提示词新增「卷纲规划」一节。用户说了卷数或章数，照用户说的拆；没说，默认每卷约 10 章（与项目5「一段」一致）；篇幅不超过一卷，只建 1 卷；未完模式只建当前这一段需要的卷。输出格式里加含 3 卷的示例并说明各字段。
3. 卷数据新增两个字段，旧卷缺字段当空处理，不报错（改 normalizeNovelVolumes）：writingRequirement（本卷写作内容要求，与摘要分开）；bridge（与下一卷的衔接点）。
4. 解析与创建：新写 parseVolumePlan（走 G1）和 applyPlannedVolumes。全新的书直接创建；已有卷的书，新增的卷以确认卡显示（「AI 建议新增 N 卷 [查看] [全部添加] [取消]」），不擅自加。已有的卷 AI 仍只能改不能删，新增的卷只能落在尚未被占用的章节范围。ensureDefaultNovelVolume 退回为「AI 没给卷纲时的兜底」。
5. 范围校验函数 validateVolumeRanges：起止章必须连续、不重叠、不超过总章数。校验不过让 AI 修正一次，仍不过按总章数均分。
6. 细纲生成只读三样（改 buildVolumeConstraintPrompt）：本卷的写作内容要求；上一卷的交接（上一卷已写完正文用实际交接，没写就用上一卷的 bridge）；本卷的 bridge（本卷结尾要给下一卷留什么）。其他卷一律不读。
7. 细纲分批按卷边界切，一批不跨两卷。
8. 与项目3衔接：改动卷纲后，相邻卷的衔接点和卷内细纲标「待核对」。

**c 验收**

- V-02 新生成的大纲有多卷，章节范围连续、不重叠
- V-03 用户说「分成 3 卷」就是 3 卷；说「共 40 章」按约每卷 10 章拆
- V-04 篇幅不超过一卷时只建 1 卷
- V-05 未完模式只建当前一段需要的卷
- V-06 写某一卷的细纲时，AI 收到的只有三样（真实上下文或抓包核对）
- V-07 第 1 卷没有上一卷、最后一卷没有下一卷，都不报错
- V-08 上一卷没写正文时用它的 bridge，不报错也不留空

## 11 已知风险（开发时重点盯）

1. 切分支换数据和存盘的读写点约 10 处，漏一处就丢细纲或存错分支。必须做「保存、刷新、导出、导入、备份恢复、突然关闭重开」闭环，并用基线标签构建的旧版本打开新存档验证主线不坏。
2. 紧急备份写在 localStorage，容量小又是兜底，分支上的恢复路径要用脚本逼出来测。
3. 沉浸模式的整屏滚动加手机软键盘，不同浏览器行为不一致，iOS 无法在本机测。
4. 团队开书一次约 8 到 15 次请求，并行加审查不一定更快，要同一段话对比实测。
5. G2 会改动大纲审阅这个现有功能，回归要逐项测。
6. 过往公告能否从 git 历史完整找回，需要先看。
7. 提示词质量决定体验：拆分、审查、卷纲规划、衔接检查、扩写 5 组，每组都要用真实案例测。
8. 存档体积会增加，S14 用夹具 C 量体积，并确认和上限提醒配合正常。

## 附录 A 用词对照（纯文字，用户会贴到用户群，不放进应用）

```
大纲：全书的总思路，讲整本书从头到尾要写什么。
卷纲：把全书分成几大段（卷）后，每一卷各自的计划。
细纲：每一章的具体计划，写正文时 AI 主要照着它写。
暗线：提前埋下、以后要回收的伏笔，记录在哪一章布置、哪一章推进、哪一章回收。
设定：世界观、人物、势力、规则等写作时要遵守的资料。
分支：从某一章分出去、另写一条新剧情线。分叉之前的内容和主线共用，分叉之后各写各的。
主线：没有分叉的原本那条线。
未完模式：只写一段（默认十章），不写结局，方便以后接着往下写。
继续规划下一段：在未完模式下，接着为下一段写大纲和细纲，已有内容不会被覆盖。
由细纲反推大纲：你已经写了细纲，让 AI 根据它倒推出大纲；没写到结局就按未完模式处理。
一段话开书：只写一段想法，AI 像团队一样分工把书的框架做出来。
拆分方案：AI 先把你的想法拆成书名、角色、卷、章等安排，你确认后才开始生成。
待核对：某一章、某一卷因为相邻内容改了，可能前后对不上，提醒你看一眼。
衔接检查：检查上一章结尾和下一章开头接不接得上。
历史：重新生成细纲前，旧的那一版会自动留下，最多保留三版，可以恢复。
红绿对比：红色是要删掉的，绿色是新增的，你可以逐处决定要不要。
设定修改：让 AI 按你的想法改已有的设定，先看改前改后，再决定用不用。
沉浸模式：隐藏侧栏和按钮、只留正文的全屏写作状态。
手写：自己动手写，AI 暂停。
扩写：让 AI 把某一处写得更长、更细，结尾、插入、选中一段、整篇四种。
标签：扩写时点在段落之间的小标记，告诉 AI 改哪里。
更新公告：每次更新后的说明，可在「关于」里重新查看。
```
